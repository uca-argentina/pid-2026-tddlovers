# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project context
- University group web app project: React frontend + Fastify backend + Postgres, fully Dockerized.
- Team works across Apple Silicon Macs (M1/M2) and at least one Windows desktop — keep cross-platform tooling in mind (line endings, shell scripts, etc.). `.gitattributes` normalizes line endings — don't remove it.
- **The app is in Spanish.** The team and its users are Argentinian, so everything user-facing is rioplatense Spanish (voseo: "Elegí", "tenés") — UI copy, validation messages, API error `message` strings, `aria-label`s/placeholders, dates and money (`Intl` with `es-AR`), and any text a proxy/error page serves. There is no i18n layer anywhere and none is planned — write the Spanish string directly. The API `error` code and `fields` keys stay English/ASCII (read by the frontend, not shown to the user). Comments in code are in Spanish too, and explain **why**, not what.

## App concept
A responsive web app (must work well on phone) that connects students and teachers.
- **Single account type**: role is chosen at signup, not separate signup flows. On the wire, in the DB, and in frontend logic the role is **`"teacher"` or `"student"`** (plus `"admin"`, see below) — English. The `user_role` enum stores this; "Docente"/"Alumno" are display text only, produced at render time. Never compare against/accept `docente`/`alumno`.
- **Admin** (`"admin"`, "Administrador" on screen): a third role that **can't be chosen at signup** (`/register` only accepts teacher/student). There is **exactly one admin account, hardcoded**: `admin@admin.com` / `ElAdmin123.` (trailing dot included), inserted by migration `013_single_admin.sql` (precomputed argon2id hash). The DB forbids any other: CHECK `users_admin_is_fixed` (role admin ⇒ that email) plus a unique partial index on `role WHERE role = 'admin'`. Don't add a way to create admins. The admin only reviews teachers, at `/admin` (`pages/Admin/AdminPage.jsx`; no calendar, bookings or search). API: `GET /api/admin/teachers?status=`, `POST /api/admin/teachers/:id/{approve,reject}` (403 for non-admins).
- **Teacher approval** (`users.approval_status`, enum `teacher_approval_status`: `pending` | `approved` | `rejected` — English on the wire, "Pendiente/Aprobado/Rechazado" on screen; NULL for non-teachers, enforced by a CHECK): every new teacher starts `pending`. While `pending` or `rejected` the teacher **can edit the profile and load availability, but doesn't show up in searches** (`listTeachers`, `findPublishedWindows` filter `approval_status = 'approved'`) **and can't receive bookings** (`POST /api/classes` and reschedule re-check it via `findWindowById`'s `teacherApprovalStatus`, since a window id can be sent anyway). The admin approves `pending`/`rejected` and rejects `pending`/`approved` ("Dar de baja": already-booked classes stay, like deleting a window). A `rejected` teacher who saves the profile goes back to `pending`. Rules live in `backend/src/lib/teacherApproval.js` (`TeacherApproval` class), mirrored in `frontend/src/utils/approval.js` only to pick buttons/notices. `request.user.approvalStatus` comes from the session; `toPublicUser` sends `approvalStatus` (null for non-teachers).
- **Teachers**: pick which subjects they teach from a fixed list (profile) and, in the same profile, set an **hourly rate per subject × modality** (`teacher_rates`, in **cents**, e.g. Matemática virtual $ 5.000/h; empty = doesn't teach it that way; 0 = free). Then they load **availability windows** from the Disponibilidad screen (a read-only week calendar + a per-day modal of cards). Each window has only: a date, optionally **repeats weekly** from that date on (so every week can differ), start/end (`:00`/`:30`, ≥30 min long), **modality** (`virtual` | `in_person` | `hybrid` — English on the wire, "Virtual/Presencial/Híbrida" on screen; virtual needs `meetingUrl`; in-person needs `locality` — the general area, e.g. "Palermo, CABA", shown to every student — **and** `address`, the exact one, shown only to students who booked; hybrid needs all three) and **capacity** `maxStudents` (1 = individual, 2–50 = group). A window can't be saved in a modality the teacher has no rate for. Windows carry **no subject, duration or price**.
- **Students**: browse offered windows (one card per window per date, showing the subjects bookable there and "desde $X/h"), filter by day/subject/modality/individual-vs-group/time, and book. The navbar search (students only — teachers don't get it) matches a subject or a teacher's name and lands on `/disponibilidad?q=…`; the board resolves `q` into filters (`utils/search.js` `resolveQuery`). There is no `/disponibilidad/:materiaId` route anymore.
- **Booking**: the student picks the **subject** (among those the teacher has a rate for in the window's modality), a **start** (`:00`/`:30`) and a **duration** (≥30 min, steps of 5, must fit before the window's end and not overlap another class of that teacher). Price = `round(hourlyRateCents × minutes / 60)`, computed by the backend (`lib/teacherRates.js`; the frontend mirrors it in `utils/rates.js` for display only). In a **group** window, other students can join an already-started class only with the **same start, subject and duration**, until it's full. Modality/link/locality/address/`price_cents` are **copied onto the class** at booking time, so later edits to the window or rates don't move booked classes. Neither the meeting link nor the exact address is ever exposed by `/api/availability` (it carries `locality` only); students see them once booked.
- **Booking lifecycle** (`class_status` enum; values in Spanish because they're shown as-is): a booking starts `pendiente` (the teacher hasn't answered, but it already holds the slot) → teacher **accepts** → `aceptada` → student **pays** → `confirmada`. Once the class has started the teacher **takes attendance** → `realizada` | `no_presentada` (allowed from `aceptada`/`confirmada`, and again to correct the mark). `cancelada` always carries a `cancelReason`: `rechazada` (teacher said no to a `pendiente`), `cancelada`, `vencida` (still `pendiente` when the class started — `expireStartedPending` runs before every class read), `reprogramada` or `vacaciones` (the teacher loaded a vacation over it).
  - **Cancel**: the teacher, any time before the start; the student, any time before the start while `pendiente`, and after that only ≥24 h before (`CANCEL_NOTICE_HOURS`).
  - **Reschedule**: student only, only a `confirmada` class, ≥24 h before. The old class becomes `cancelada`/`reprogramada` and a new booking is created `pendiente` with `rescheduledFrom` — it has to be accepted and paid again. Same teacher and subject; the UI is the booking board with `?reprogramar=<classId>`.
  - **Payment** is tracked apart from the status (`paidAt`): a class can be paid when `aceptada` (→ `confirmada`) or after it happened (`realizada`/`no_presentada` keep their status), never twice. **Nothing is actually charged** — `POST /api/classes/:id/pay` only records `paid_at`; there's no payment provider.
  - Endpoints: `POST /api/classes/:id/{accept,cancel,pay,attendance,reschedule}`, each returns the updated class (reschedule returns the new one).
  - The rules live in `backend/src/lib/classStates.js` (`checkAction`), which is authoritative. `frontend/src/utils/classStates.js` mirrors them **only** to decide which buttons to show (`allowedActions`) — change a rule in both places; the backend re-checks and explains in its error `message`.

- **Class packs** (`class_packs` = what a teacher offers, `student_packs` = what a student bought; migrations `014` + `015`): the teacher offers packs from `/paquetes` — `classCount` 2–100, **`classMinutes`** (fixed length of each pack class, 30–240, steps of 5), total `priceCents`, `validityDays` 1–365 counted from the purchase day, inclusive — and can only *deactivate* one (bought packs reference it). The student buys from `/paquetes` (`POST /api/packs/:id/buy`; nothing is charged, like `pay`), which copies count, minutes and price and sets `expires_on`. A pack covers **any class of that teacher**: the student still picks subject, modality (window) and duration, and books with **`packId` + `packTokens`** (how many pack classes this booking uses, ≥1; `classes.student_pack_id`, `classes.pack_tokens`). Tokens can't cover more than the class lasts (`packTokens × classMinutes ≤ durationMinutes`); the rest is paid at the subject's hourly rate (`price_cents` = extra only, e.g. 1 h 30 with one 1 h token pays 30 min). Accepting a class the pack covers entirely (`price_cents` 0) goes straight to `confirmada` with `paid_at`; with an extra it goes to `aceptada` and is paid as usual. **Each attendance (`realizada`) uses that booking's `pack_tokens`**; what's left is never stored, it's summed from the pack's classes (`remaining` = count − Σ tokens of realizadas; `available` = remaining − Σ tokens of pendiente/aceptada/confirmada), so correcting attendance or cancelling gives them back. `no_presentada` uses none. Rescheduling can use tokens too (the old class's are freed in the same transaction). Rules: `backend/src/lib/classPacks.js` (`StudentPack`, `validatePackOffer`, `expiryFor`); `db/classes.js` re-checks room and expiry under a per-pack advisory lock. Only approved teachers' packs are listed/buyable. The booking board shows "Te quedan N clases de 1 h del paquete" on that teacher's cards and the booking modal has a − N + stepper (defaults to as many as fit) with what's covered and what's paid apart (`utils/packs.js`). API: `GET/POST /api/teachers/me/packs`, `DELETE /api/teachers/me/packs/:id`, `GET /api/packs[?teacherId]`, `GET /api/packs/mine`, `POST /api/packs/:id/buy`.

- **Teacher vacations** (`teacher_vacations`, migration `016`): from Disponibilidad ("Vacaciones" button next to "Agregar horario", `VacationsDialog`) the teacher loads one or more date ranges (`startDate`–`endDate`, both inclusive, ≤365 days, not already over; ranges of the same teacher can't overlap — exclusion constraint + check under a per-teacher lock) and can delete them. During a vacation the windows stay saved but **nothing is bookable**: `GET /api/availability` still returns those rows with `onVacation: true` and empty `free`/`groups`, so the student sees the card greyed with "El docente está de vacaciones este día" (not counted as libres); the teacher's week shows those days striped with a "Vacaciones" tag. `POST /api/classes` (and reschedule) reject a vacation date (route check + re-check inside `insertClass` under the teacher+date lock). **Saving a vacation cancels the teacher's not-yet-started `pendiente`/`aceptada`/`confirmada` classes in the range** in the same transaction, with `cancel_reason = 'vacaciones'` (`cancelled_by` teacher); `GET /api/teachers/me/vacations/impact?startDate&endDate` tells how many before saving. Deleting a vacation does **not** revive them. Rules: `backend/src/lib/vacations.js` (`VacationRange`). API: `GET/POST /api/teachers/me/vacations`, `GET /api/teachers/me/vacations/impact`, `DELETE /api/teachers/me/vacations/:id`.

### The one design decision to understand across front and back: windows → dated availability
A teacher saves windows via `POST/PUT/DELETE /api/teachers/me/availability[/:id]`; `GET /api/teachers/me/availability?from&to` returns the raw windows that fall in the range (the teacher screen places them with `utils/windows.js` `occursOn`). A student books a **date**. `GET /api/availability` returns one row per **(window, date)**, already net of what's booked, via `backend/src/lib/availabilityExpansion.js`: `subjects: [{ id, name, hourlyRateCents }]` (the teacher's rates in that modality), `free: [{ start, end }]` (stretches with no class of that teacher; `start` is the first `:00`/`:30`, `end` any minute) and `groups: [{ start, end, subjectId, subjectName, enrolled }]` (joinable group classes). There's no closed list of slots because the student picks the duration; the frontend derives start options and max durations (`utils/booking.js` `startOptions`) and the backend re-validates on `POST /api/classes`. Windows whose modality has no rate aren't offered. Two different meanings of "booked", only one subtracted:
- Booked **with that teacher** → subtracted (except remaining seats in a group class, offered in `groups`).
- Booked by **this student with someone else** → not subtracted; the frontend greys those starts out using the student's own non-cancelled classes (`fetchMyLessons` → `GET /api/classes?from&to`, which returns the logged-in user's classes — the session decides whose) and `annotateClashes`.

Everything that isn't `cancelada` occupies the slot, `pendiente` included (the exclusion constraints are `WHERE status <> 'cancelada'`).

Rules the backend must enforce (the UI already does, but the UI can be bypassed): window start/end and class **starts** on `:00`/`:30` (class **ends** land wherever the duration puts them, in steps of 5 min, e.g. 13:45); class duration ≥30 min and within the window; rates in whole cents and only for subjects in the profile (`teacher_rates` FKs `teacher_subjects`, so dropping a subject drops its rates); a teacher's windows can't overlap on any date (weekly vs one-off included — checked in `db/availability.js` under an advisory lock, not a DB constraint); a window's modality must have at least one rate; a teacher never gives two classes at once (exclusion constraint allows only same-start group rows); joining a group requires same subject and duration, plus capacity (checked in `bookClass` under a per-teacher+date lock); a student can't have overlapping classes even by a minute; the booked subject must have a rate in the window's modality.

## Local dev ports
- Frontend: `127.0.0.1:5173`
- Backend: `127.0.0.1:4000`
- Postgres: `127.0.0.1:5432` (not exposed publicly in production — only reachable from the backend container)

Use `127.0.0.1`, not `localhost`: on macOS `localhost` resolves to `::1` first, and if any other project's dev server is bound to `[::1]:5173` it silently wins over Docker's wildcard bind. Check with `lsof -nP -iTCP:5173 -sTCP:LISTEN`.

## Commands
Run these from inside the respective subfolder (`frontend/` or `backend/`), not from the repo root — there's no root-level `package.json`.

**Frontend**
- `npm run dev` — Vite dev server (not `npm start`, that's a CRA habit).
- `npm test` — vitest + jsdom + Testing Library. Tests are colocated (`Thing.jsx` → `Thing.test.jsx`).
- `npm run lint` — must pass before pushing, along with `npm test`.
- Test data: build API-shaped objects with `src/testing/fixtures.js` — `apiClass()` (a class exactly as `/api/classes` returns it), `apiUser()` (as login/`/me`/profile return it) and `updatedUser()` (the `PATCH /api/users/me` response) — and override only what the test cares about. Don't hand-write partial classes/users: tests end up passing on a shape the API no longer sends. Mock client functions with the real response shape (unwrapped objects, never `{ user }` / `{ lesson }`).

**Backend**
- Tests: vitest, colocated (`index.js` → `<area>.test.js`), using `buildApp()` + `app.inject()` (no real port). See `src/app.test.js` for the pattern. The `db/*` modules are mocked; mock them with the rows they really return (e.g. `clase()` in `routes/classes/classes.test.js` mirrors `CLASS_COLUMNS`).
- Migrations: plain `.sql` in `migrations/`, no runner. On a **fresh** database volume Postgres applies them all automatically (`docker-compose.dev.yml` mounts the folder into `docker-entrypoint-initdb.d`); on an existing database apply each **new** one by hand, once, in filename order — `psql "$DATABASE_URL" -f migrations/0NN_*.sql` — and tell the team, since everyone has their own local DB. Write new ones idempotently (`IF NOT EXISTS`, guarded `DO` blocks) so an accidental re-run is harmless. **Never re-run 003–006 on an existing database**: they predate later schema changes, fail midway, and since files don't run in a transaction the statements before the failure stick (re-running 006 drops `classes_teacher_no_overlap` before erroring).

**Infra / Docker**
- Dev stack: `docker compose -f docker-compose.dev.yml up --build`.
- After changing dependencies in either app, rebuild with `-V` (not just `--build`): `docker compose -f docker-compose.dev.yml up --build -V`. Both app services mount an anonymous `/app/node_modules` volume that Docker seeds only once and then persists across rebuilds, shadowing a freshly built image's deps — symptom is `Failed to resolve import "<package>"` in the browser/server despite a clean build. **Never use `down -v`** — that also wipes the named `pgdata_dev` volume and deletes the database.

## Cross-cutting conventions
- **Style differs on purpose between the two app repos** — match whichever folder you're editing, don't impose one on the other, and don't run a formatter (neither has a prettier config):
  - `backend/`: semicolons, single quotes, 2-space indent, ~100 cols.
  - `frontend/`: no semicolons, single quotes, 2-space indent, ~100 cols. Class components only — hooks are banned except in the one bridge file `src/routes/withRouter.jsx`, which hands components a single `router` prop (`navigate`, `location`, `params`, `searchParams`, `setSearchParams`).
- **IDs are opaque UUID strings** (`gen_random_uuid()`), never numbers — don't coerce with `Number()`, compare with `String(a) === String(b)`.
- **Dates** are `"YYYY-MM-DD"` local time, no timezone/`Z`. "Now" on the backend is Argentina time via `backend/src/lib/clock.js` — the container runs in UTC, so never use `new Date()` getters or `toISOString()` for today. **Times** are `"HH:MM"` 24h; starts are always `:00`/`:30`, a class end can be any minute. A range's `end` is exclusive; midnight is written `"24:00"`, never `"00:00"`. Weekday keys are ASCII lowercase without accents (`lunes` … `domingo`), week starts Monday — these are JSON/DB values, not display text.
- Check `pwd` before `npm install` — `package-lock.json` has repeatedly ended up committed to the wrong subfolder.
- No backwards-compatibility code for old data shapes: every migration is applied to every DB, so the frontend can rely on the schema as it is now (e.g. a class always has `modality`, `maxStudents` and `priceCents` — `NOT NULL` since 009). Don't add "legacy row" branches; if old data needs handling, fix it in a migration.
