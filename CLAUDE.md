# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project context
- University group web app project: React frontend + Fastify backend + Postgres, fully Dockerized.
- Team works across Apple Silicon Macs (M1/M2) and at least one Windows desktop — keep cross-platform tooling in mind (line endings, shell scripts, etc.). `.gitattributes` normalizes line endings — don't remove it.
- **The app is in Spanish.** The team and its users are Argentinian, so everything user-facing is rioplatense Spanish (voseo: "Elegí", "tenés") — UI copy, validation messages, API error `message` strings, `aria-label`s/placeholders, dates and money (`Intl` with `es-AR`), and any text a proxy/error page serves. There is no i18n layer anywhere and none is planned — write the Spanish string directly. The API `error` code and `fields` keys stay English/ASCII (read by the frontend, not shown to the user). Comments in code are in Spanish too. Every important function has a header saying what it does, what it receives (`@param`, including where each argument comes from: which endpoint, query, prop or caller), what it returns, and who uses it ("Lo usa/Lo usan: …"), so data can be traced across files; inside the body, comments explain **why**. Keep those headers up to date when you change a function or its callers.

## App concept
A responsive web app (must work well on phone) that connects students and teachers.
- **Single account type**: role is chosen at signup, not separate signup flows. On the wire, in the DB, and in frontend logic the role is **`"teacher"` or `"student"`** (plus `"admin"`, see below) — English. The `user_role` enum stores this; "Docente"/"Alumno" are display text only, produced at render time. Never compare against/accept `docente`/`alumno`.
- **Admin** (`"admin"`, "Administrador" on screen): a third role that **can't be chosen at signup** (`/register` only accepts teacher/student). There is **exactly one admin account, hardcoded**: `admin@admin.com` / `ElAdmin123.` (trailing dot included), inserted by migration `013_single_admin.sql` (precomputed argon2id hash). The DB forbids any other: CHECK `users_admin_is_fixed` (role admin ⇒ that email) plus a unique partial index on `role WHERE role = 'admin'`. Don't add a way to create admins. The admin only reviews teachers, at `/admin` (`pages/Admin/AdminPage.jsx`; no calendar, bookings or search). API: `GET /api/admin/teachers?status=`, `POST /api/admin/teachers/:id/{approve,reject}` (403 for non-admins).
- **Teacher approval** (`users.approval_status`, enum `teacher_approval_status`: `pending` | `approved` | `rejected` — English on the wire, "Pendiente/Aprobado/Rechazado" on screen; NULL for non-teachers, enforced by a CHECK): every new teacher starts `pending`. While `pending` or `rejected` the teacher **can edit the profile and load availability, but doesn't show up in searches** (`listTeachers`, `findPublishedWindows` filter `approval_status = 'approved'`) **and can't receive bookings** (`POST /api/bookings` and reschedule re-check it via `findWindowById`'s `teacherApprovalStatus`, since a window id can be sent anyway). The admin approves `pending`/`rejected` and rejects `pending`/`approved` ("Dar de baja": already-booked classes stay, like deleting a window). A `rejected` teacher who saves the profile goes back to `pending`. Rules live in `backend/src/lib/teacherApproval.js` (`TeacherApproval` class), mirrored in `frontend/src/utils/approval.js` only to pick buttons/notices. `request.user.approvalStatus` comes from the session; `toPublicUser` sends `approvalStatus` (null for non-teachers).
- **Teachers**: pick which subjects they teach from a fixed list (profile) and, in the same profile, set an **hourly rate per subject × modality** (`teacher_rates`, in **cents**, e.g. Matemática virtual $ 5.000/h; empty = doesn't teach it that way; 0 = free). Then they load **availability windows** from the Disponibilidad screen (a read-only week calendar + a per-day modal of cards). Each window has only: a date, optionally **repeats weekly** from that date on (so every week can differ), start/end (`:00`/`:30`, ≥30 min long), **modality** (`virtual` | `in_person` | `hybrid` — English on the wire, "Virtual/Presencial/Híbrida" on screen; virtual needs `meetingUrl`; in-person needs an **address** (see Teacher addresses below); hybrid needs both) and **capacity** `maxStudents` (1 = individual, 2–50 = group). A window can't be saved in a modality the teacher has no rate for. Windows carry **no subject, duration or price**.
- **Students**: browse offered windows (one card per window per date, showing the subjects bookable there and "desde $X/h"), filter by day/subject/modality/individual-vs-group/time, and book. The navbar search (students only — teachers don't get it) suggests subjects and teachers by name (`utils/search.js` `suggest`; `GET /api/teachers` only lists approved teachers with a rated subject **and a publishable window from today on**, so a suggestion never leads to an empty board) and lands on `/disponibilidad?q=…`. The board resolves `q` with `utils/search.js` `resolveQuery`: if `q` is **exactly** a subject's name (ignoring accents/case) it's a subject filter; otherwise it's free text matched against teacher **and** subject names (chip "Búsqueda: X"). It's exact on purpose: with "starts with", "Ana" landed on Análisis. There is no `/disponibilidad/:materiaId` route anymore.
- **Booking**: the student picks the **subject** (among those the teacher has a rate for in the window's modality), a **start** (`:00`/`:30`) and a **duration** (≥30 min, steps of 5, must fit before the window's end and not overlap another class of that teacher). Price = `round(hourlyRateCents × minutes / 60)`, computed by the backend (`lib/teacherRates.js`; the frontend mirrors it in `utils/rates.js` for display only). In a **group** window, other students can join an already-started class only with the **same start, subject and duration**, until it's full. Joining adds a booking to the existing **class**, which keeps what was copied from the window on its first booking (modality, `maxStudents`, link, address); capacity is measured against the class's `maxStudents` — the teacher may have edited the window since. If the class's modality differs from the window's current one the join is a 409 (the rate was looked up in the window's modality). `/api/availability` uses the same class values, so what it offers is what `POST /api/bookings` accepts. Modality/link/locality/address/`price_cents` are **copied onto the class** at booking time (`classes.address`, on the class, = the address formatted as one line by `lib/addresses.js` `formatAddress`, `classes.locality` = its locality), so later edits to the window, its address or the rates don't move booked classes. Neither the meeting link nor the exact address is ever exposed by `/api/availability` (it carries `locality` only). Students see the link once booked, but the **exact address only once the class is paid** (or free: `priceCents` 0, which includes classes fully covered by a pack); before that `/api/bookings` sends `address: null` and the UI shows the locality plus "La dirección exacta aparece cuando pagues la clase." — `lib/bookingStates.js` `canSeeExactAddress`/`forViewer`, applied to every booking response for a student. Teachers always see it.
- **Tables: a class vs. each student's booking** (migration `023`): `classes` is the **class** (teacher, subject, date, start/end, the window it came from and what was copied from it — modality, `max_students`, link, address, locality); a group class with 5 students is **one row**. `class_bookings` is **each student's booking** in it: status, `price_cents`, `paid_at`, pack (`student_pack_id`, `pack_tokens`), Neuronas redemption (`reward_type`, `reward_neuronas`), cancellation and `rescheduled_from`. Every way of paying lives in the booking, since students of the same class can pay differently. **Two ids, never mixed**: a booking's `id` (`/api/bookings/:id`, `?reprogramar=<id>`, `excludeBookingId`, `booking:<id>` credit keys) and its **`classId`** = `classes.id` (`/api/classes/:classId/…`, the frontend's `classKey`, `homeworks.class_id`). Booking ids are the pre-`023` row ids, so nothing already stored changed. Details:
  - `class_bookings` keeps a copy of `class_date`/`start_time`/`end_time`, tied to the class by a composite FK with `ON UPDATE CASCADE` (can't drift), so `class_bookings_student_no_overlap` can stay in the DB.
  - `classes.active` = has a non-cancelled booking. It's maintained **only by the trigger** `class_bookings_sync_active` — never set it by hand. `classes_teacher_no_overlap` only looks at active classes, so a class cancelled for everyone frees the slot and stays as history; booking that slot again creates a **new** class.
  - Joining a group = inserting a booking into the active class of that start (`db/bookings.js` `insertBooking`); the first booking of a start creates the class with the window's data.
  - **No view: every read joins explicitly** (`FROM class_bookings b JOIN classes c ON c.id = b.class_id`, `b.` = booking, `c.` = class; `BOOKING_COLUMNS`/`BOOKING_JOINS` in `db/bookings.js`); writes go to the right table (`UPDATE class_bookings …` for status/payment; `classes` only on creation). The status enum is **`booking_status`**.
  - Everything that belongs to the class hangs from `classes.id` (migration `024`): material (`class_materials.class_id`, files by `class_id`), group homework (`homeworks.class_id`; its date/time/subject come from the class), the teacher's Neuronas for giving it (`taught:<classId>`) and the whole-class actions (`POST /api/classes/:classId/{accept,cancel}`).
  - Backend modules: `db/bookings.js` (bookings: `findBookingsForUser`, `findBookingById`, `findClassBookings`, `findStudentBooking`, `createBooking`, `rescheduleBooking`, `transitionBooking(s)`, `expireStartedPending`), `db/classes.js` (classes alone: `findClass`, `findActiveClasses`); routes `routes/bookings` (`/api/bookings`) and `routes/classes` (`/api/classes/:classId/…`: whole-class actions and material).
  - Frontend: a "class" on screen is the group of bookings sharing a `classId` (`utils/reservations.js` `groupClasses`/`classKey`); `components/BookingActions.jsx` acts on one booking, `components/ClassActions.jsx` on the whole class.
- **Booking lifecycle** (`booking_status` enum; values in Spanish because they're shown as-is): a booking starts `pendiente` (the teacher hasn't answered, but it already holds the slot) → teacher **accepts** → `aceptada` → student **pays** → `confirmada`. Once the class has started the teacher **takes attendance** → `realizada` | `no_presentada` (allowed from `aceptada`/`confirmada`, and again to correct the mark). `cancelada` always carries a `cancelReason`: `rechazada` (teacher said no to a `pendiente`), `cancelada`, `vencida` (still `pendiente` when the class started — `expireStartedPending` runs before every booking read), `reprogramada` or `vacaciones` (the teacher loaded a vacation over it).
  - **Cancel**: the teacher, any time before the start; the student, any time before the start while `pendiente`, and after that only ≥24 h before (`CANCEL_NOTICE_HOURS`).
  - **Reschedule**: student only, only a `confirmada` class, ≥24 h before. The old class becomes `cancelada`/`reprogramada` and a new booking is created `pendiente` with `rescheduledFrom` — it has to be accepted and paid again. Same teacher and subject; the UI is the booking board with `?reprogramar=<classId>`.
  - **Payment** is tracked apart from the status (`paidAt`): a booking can be paid when `aceptada` (→ `confirmada`) or after it happened (`realizada`/`no_presentada` keep their status), never twice. **Nothing is actually charged** — `POST /api/bookings/:id/pay` only records `paid_at`; there's no payment provider.
  - Endpoints: `POST /api/bookings/:id/{accept,cancel,pay,attendance,reschedule}`, each returns the updated booking (reschedule returns the new one).
  - The rules live in `backend/src/lib/bookingStates.js` (`checkAction`, `applyAccept`, `applyCancel`), which is authoritative. `frontend/src/utils/bookingStates.js` mirrors them **only** to decide which buttons to show (`allowedActions`) — change a rule in both places; the backend re-checks and explains in its error `message`.

- **Class packs** (`class_packs` = what a teacher offers, `student_packs` = what a student bought; migrations `014` + `015`): the teacher offers packs from `/paquetes` — `classCount` 2–100, **`classMinutes`** (fixed length of each pack class, 30–240, steps of 5), total `priceCents`, `validityDays` 1–365 counted from the purchase day, inclusive — and can only *deactivate* one (bought packs reference it). The student buys from `/paquetes` (`POST /api/packs/:id/buy`; nothing is charged, like `pay`), which copies count, minutes and price and sets `expires_on`. A pack covers **any class of that teacher**: the student still picks subject, modality (window) and duration, and books with **`packId` + `packTokens`** (how many pack classes this booking uses, ≥1; `class_bookings.student_pack_id`, `class_bookings.pack_tokens`). Tokens can't cover more than the class lasts (`packTokens × classMinutes ≤ durationMinutes`); the rest is paid at the subject's hourly rate (`price_cents` = extra only, e.g. 1 h 30 with one 1 h token pays 30 min). Accepting a class the pack covers entirely (`price_cents` 0) goes straight to `confirmada` with `paid_at`; with an extra it goes to `aceptada` and is paid as usual. **Each attendance (`realizada`) uses that booking's `pack_tokens`**; what's left is never stored, it's summed from the pack's classes (`remaining` = count − Σ tokens of realizadas; `available` = remaining − Σ tokens of pendiente/aceptada/confirmada), so correcting attendance or cancelling gives them back. `no_presentada` uses none. Rescheduling can use tokens too (the old class's are freed in the same transaction). Rules: `backend/src/lib/classPacks.js` (`StudentPack`, `validatePackOffer`, `expiryFor`); `db/classes.js` re-checks room and expiry under a per-pack advisory lock. Only approved teachers' packs are listed/buyable. `GET /api/packs/mine` lists every pack the student bought (also expired ones, or from a teacher no longer approved) with `remaining`, `available`, `expired`, `teacherApproved` and **`usable`** (not expired, `available > 0`, teacher approved — computed by `StudentPack#summary`; the frontend never recomputes it, except `packsForReschedule`, which adds back the old class's tokens). The pack for a given card/date is always `utils/packs.js` `usablePackFor` (the usable one that expires first and still covers that date) — the **same** one on the board card ("Te quedan N clases de 1 h del paquete") and in the booking modal, which has a − N + stepper (defaults to as many as fit) with what's covered and what's paid apart. An expired pack shows "Sin usar: N" in `/paquetes`, never "Te quedan". API: `GET/POST /api/teachers/me/packs`, `DELETE /api/teachers/me/packs/:id`, `GET /api/packs[?teacherId]`, `GET /api/packs/mine`, `POST /api/packs/:id/buy`.

- **Teacher vacations** — shown on screen as **"Licencia"** (`teacher_vacations`, migration `016`; internal names — table, `/vacations` routes, `VacationsDialog`, `cancel_reason = 'vacaciones'` — stay as they are, only user-facing text says licencia): from Disponibilidad ("Licencia" button next to "Agregar horario", `VacationsDialog`) the teacher loads one or more date ranges (`startDate`–`endDate`, both inclusive, ≤365 days, not already over; ranges of the same teacher can't overlap — exclusion constraint + check under a per-teacher lock) and can delete them. During a vacation the windows stay saved but **nothing is bookable**: `GET /api/availability` still returns those rows with `onVacation: true` and empty `starts`/`groups`, so the student sees the card greyed with "El docente está de licencia este día" (not counted as "para reservar"); the teacher's week shows those days striped with a "Licencia" tag. `POST /api/bookings` (and reschedule) reject a vacation date (route check + re-check inside `insertBooking` under the teacher+date lock). **Saving a vacation cancels the teacher's not-yet-started `pendiente`/`aceptada`/`confirmada` classes in the range** in the same transaction, with `cancel_reason = 'vacaciones'` (`cancelled_by` teacher); `GET /api/teachers/me/vacations/impact?startDate&endDate` tells how many before saving. Deleting a vacation does **not** revive them. Rules: `backend/src/lib/vacations.js` (`VacationRange`). API: `GET/POST /api/teachers/me/vacations`, `GET /api/teachers/me/vacations/impact`, `DELETE /api/teachers/me/vacations/:id`.

- **Teacher addresses** (`teacher_addresses`, migration `019`): a teacher's in-person locations, each with `label` ("Casa", "Escuela"), `street`, `number`, `postalCode`, **`locality`** (the only part students see before paying), `city`, and optional `floor`, `apartment`, `notes`. Managed from the profile (`pages/Profile/AddressesSection.jsx` + `AddressDialog.jsx`: add, edit, delete, "Usar como predeterminada"); at most one `isDefault` per teacher (unique partial index; the first saved one becomes default), preselected when creating a window. **Windows point to an address** (`availability.address_id`, composite FK `(address_id, teacher_id)` so it must be the same teacher's, `ON DELETE RESTRICT`): editing "Casa" updates every window using it, and an address in use can't be deleted (409 saying how many windows use it). In the window form (`WindowForm` → `components/AddressFields.jsx`) the teacher picks a saved one or "Otra dirección…" and types it, optionally ticking "Guardar esta dirección" (then it needs a name and is saved like one from the profile). An unsaved one is a row with `saved = false`, not listed in the profile, deleted by `db/availability.js` once no window uses it. The window payload carries either `addressId` or `address: {…}` + `saveAddress`; windows come back with `address: {id, label, saved, isDefault, street, …}` and a top-level `locality`. Rules: `backend/src/lib/addresses.js` (mirrored in `frontend/src/utils/addresses.js`). Locks: always the teacher's availability lock first, then the addresses one (`db/addresses.js` `lockAddresses`). API: `GET/POST /api/teachers/me/addresses`, `PUT/DELETE /api/teachers/me/addresses/:id`, `POST /api/teachers/me/addresses/:id/default`.

- **Favorite teachers** (`favorite_teachers`, migration `017`; PK `(student_id, teacher_id)`): students only. A heart (`components/FavoriteButton.jsx`, which makes the request itself and reports via `onChange`/`onError`) on the booking board cards and on each class in Mis reservas; `/favoritos` (`pages/Favorites/FavoritesPage.jsx`, navbar link hidden for teachers) lists them with their rated subjects and a "Ver horarios" link to `/disponibilidad?q=<name>`; the board has a "Solo favoritos" chip (`filterCards` `teacherIds`). The screens that show hearts (BookingBoard, CalendarPage, ReservationsPage) get the favorites from the class HOC `routes/withFavorites.jsx` (`favoriteIds` — null if not a student or the request failed, so no hearts are shown — `favoriteError`, `onFavoriteChange`, `onFavoriteError`); don't load favorites per screen again. Private — teachers see nothing. Only **approved** teachers can be added and are listed; a favorite whose teacher stops being approved stays stored but hidden, and reappears if re-approved. API: `GET /api/favorites`, `PUT /api/favorites/:teacherId` (idempotent; 404 if not an approved teacher), `DELETE /api/favorites/:teacherId` (idempotent).

- **Class material** (`class_materials` + `class_material_files`, migration `018`): once a class has **ended** (`aceptada`/`confirmada`/`realizada`/`no_presentada`), its teacher leaves a summary (≤5000 chars) and attachments of any type (≤10 MB each, ≤20 files and ≤25 MB per class); its students see them from then on (also if marked `no_presentada`). Keyed by the **class** (`class_id`, migration `024`), not by booking, so in a group class all enrolled students see the same material. Files live in an **S3 bucket, not in Postgres** (Neon free is 0.5 GB; Render's disk is wiped on deploy): `class_material_files.storage_key` points to the object (new keys are `materials/<classId>/<id>`; keys from before `024` keep their old `materials/<teacher>/<date>/<HHMM>/<id>` shape and still work, since the key is always read from the DB), and name/type/size stay in Postgres for listing and limits. All bucket access goes through `backend/src/storage/files.js` (AWS SDK v3; mock it in route tests like `db/*`). Upload = check limits → put objects → insert rows (objects are deleted if the insert is refused); delete = row first, then object; download = access check, then a **302 to a presigned GET valid 5 min** that carries `response-content-disposition` (`attachment` for everything except png/jpeg/gif/webp, which are `inline`, so an uploaded .html/.svg never renders). Classes carry `hasMaterial`.
  - **Production (Render + Neon) uses the Backblaze B2 bucket `pid-tddlovers`, and only production.** Its keys exist only in Render's env (`S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`). **Never point a local environment at B2, never put its keys in `.env`, the repo or a chat.**
  - **Local dev always uses MinIO** from `docker-compose.dev.yml` (image `pgsty/minio`, a community fork — official MinIO images are no longer published), bucket `pid-tddlovers-dev`, created by the one-shot `minio-init` service. The backend reaches it at `http://minio:9000` and signs links for `S3_PUBLIC_ENDPOINT=http://127.0.0.1:9000`, since the signature includes the host the browser uses. Rules: `backend/src/lib/classMaterials.js` (mirrored in `frontend/src/utils/classMaterials.js`). Upload is multipart via `@fastify/multipart`, registered only inside the classes plugin. API (by the class's id, not a booking's): `GET/PUT /api/classes/:classId/material`, `POST /api/classes/:classId/material/files`, `GET/DELETE /api/classes/:classId/material/files/:fileId`. The teacher may see/edit it if any booking of the class could happen (`materialStatusOf`); a student, with their own booking in it.
- **Homework** — shown on screen as **"Tareas"** (`homeworks`, `homework_submissions`, `homework_messages`, migration `020`; `/tareas`, `pages/Homework/`, in the sidebar and, on phones, a row in Perfil since the tab bar stays at five): the teacher assigns a homework (`title`, optional `description`, `dueDate` + `dueTime` in Argentina time) to **one of their students** (any student with a non-cancelled class with them) or to **one of their group classes** (from the last 60 days on; `homeworks.class_id`, and the date/time/subject shown come from that class). `homeworks` is the assignment; `homework_submissions` has **one row per assigned student, created empty at assignment**: recipients are fixed then (a later join doesn't receive it; cancelling or rescheduling doesn't remove it), and in a group class each student submits and is corrected separately. The student submits a text and/or a link (http/https only, because it's rendered as `<a href>`; re-checked in `SubmissionContent`) and may change it until it's corrected. Submitting after the deadline is allowed and stores `is_late` ("Fuera de término"), recalculated on every change; an unsubmitted overdue one shows "Vencida". The teacher corrects with a `feedback` text and can update it. Each submission has a chat (`HomeworkChat.jsx`), open from submission on, also after correction; there are no websockets, so it polls every 5 s while open and the tab is visible. Students only see their own submission. A foreign submission is a 404. Rules: `backend/src/lib/homework.js` (mirrored in `frontend/src/utils/homework.js`). `GET /api/homework` answers by session role (`submissions` for teachers, `submission` for students). App mounts no screen until `/api/auth/me` answers (`routes/SessionLoading.jsx` goes in place of `AppLayout` while `sessionChecked` is false), so screens never start with a guessed role; `HomeworkPage` still discards an answer requested with a previous `viewRole` (`fetchToken`). API: `GET/POST /api/homework`, `GET /api/homework/targets`, `PUT /api/homework/:id/submission`, `POST /api/homework/submissions/:id/feedback`, `GET/POST /api/homework/submissions/:id/messages`.
- **Neuronas** (`neurona_credits`, `teacher_featured`, `class_bookings.reward_type`/`reward_neuronas`, `users.accepts_neurona_rewards`, migration `021`; `/neuronas`, `pages/Neuronas/`, in the sidebar and, on phones, a row in Perfil): points students and teachers earn and spend. Nothing is charged, so a redeemed class is absorbed by the teacher: redemptions only work with teachers who opted in (`PUT /api/teachers/me/accepts-rewards`, a separate endpoint because saving the profile sends a rejected teacher back to `pending`; toggle in Perfil, `NeuronasSetting.jsx`).
  - **A class counts** when `realizada` and: `price_cents > 0` with `paid_at`; or `price_cents = 0` and covered by a redemption (teacher only) or by a pack with price > 0. **`paid_at` alone isn't enough**: accepting a class covered by a $ 0 pack sets it, and `pay` accepts a free class. $ 0 classes never earn. A class with a redemption never earns the student anything. A teacher–student pair counts up to 8 h per week (Mon–Sun), looking only at earlier classes so marking order doesn't matter.
  - **Earning**: student 10/h (proportional) and 10 per on-time homework (max 3 per week per teacher); teacher 10/h × (1 + 0.5 per extra counted student, up to 10; max 150 per class date), the first correction 10/6/3/0 at <24 h, 24–72 h, 72–168 h, more (max 50 per day; needs ≥20 chars) and half of what the student spent when a redeemed class is given (no cap). The correction clock starts at the later of `submitted_at` (overwritten on each edit) and the deadline, since correcting closes the submission. Re-correcting pays nothing. A homework with <24 h between creation and deadline pays nobody. The student gets paid on the first correction, or 7 days after the deadline if it never comes (`settleHomeworkCredits`, no cron: runs when the student reads or spends their balance); editing after the deadline removes it.
  - **Spending**: on booking and reschedule, `rewardType` = `free_30` (500), `free_60` (1000), `discount_10` (250), `discount_20` (500). Free ones cover their minutes, the rest is paid at the rate, and they can't exceed the class length; discounts apply to the first 60 min. Not combinable with a pack; not on a $ 0 rate. Fully covered → accepting goes straight to `confirmada` with `paid_at`. Teachers buy **Destacado**: 7 days from today (Argentina date, `clock.js`) for 1000, max 5 active at once — the cap counts only **approved** teachers' Destacados (`featuredActiveOn` SQL fragment in `db/neuronas.js`, shared by the cap and the board) — listed first per day on the board with a tag (`groupCardsByDate`), except while on vacation (the row comes with `teacherFeatured: false`).
  - **The balance is never stored**: Σ credits − Σ `reward_neuronas` of non-cancelled classes − Σ Destacados, so cancelling returns a redemption by itself. It can go negative after an attendance correction; that only blocks new redemptions. **Level** comes from Σ credits (Neurona 0, Sinapsis 200, Red neuronal 600, Mente brillante 1500), so spending never lowers it. Student badges are computed from credit counts.
  - `db/neuronas.js` `syncClassCredits` recalculates a class from its current state (upsert or delete, keyed `booking:<bookingId>`, `taught:<classId>`, `bonus:<bookingId>`; `submission:<id>` for homework), inside `transitionBookings`'s transaction when marking attendance or paying, which is how corrections revert. Rules and numbers: `backend/src/lib/neuronas.js` (mirrored in `frontend/src/utils/neuronas.js`, change costs in both). Fake accounts can still "pay" because nothing is charged: the caps limit that abuse, they don't remove it. API: `GET /api/neuronas` (by session role: `badges` for students, `featured` for teachers), `POST /api/neuronas/featured`.
- **Mis reservas** (`pages/Reservations/ReservationsPage.jsx`): "Próxima clase" / "Última clase" cards (a running class counts as next), then 5 category cards (Pendientes/Aceptadas/Confirmadas with a count; Finalizadas = realizada+no_presentada and Canceladas without one) that open a `Modal tall` list (upcoming nearest first, closed newest first). **One card per class, not per booking** (`utils/reservations.js` `groupClasses`/`classesIn`, grouped by `classId`; "not cancelled" is always `activeRows`, the "Individual / Grupal · n de M" label is always `classCapacityLabel`, the Calendar uses `calendarClasses`, and its "Tenés N clases con solicitudes esperando respuesta" notice counts classes with `pendingClassCount`, not bookings): a group class with a pending and a confirmed student shows in both categories; Canceladas only holds classes cancelled for everyone. Cards (`components/ClassCard.jsx`, also the Calendar's `DayAgenda`) never show student names — just Individual / Grupal · n de M — and the teacher's card buttons act on the whole class (`components/ClassActions.jsx`: "Aceptar a los N", "Cancelar clase" for all) through `POST /api/classes/:classId/{accept,cancel}`, which applies the same `checkAction` rules to every non-cancelled booking of that class **all-or-nothing** (`transitionBookings`, one transaction; 409 if any changed meanwhile) and returns the updated bookings. One booking's own buttons are `components/BookingActions.jsx`. Tapping a class opens `components/ClassDetailDialog.jsx`: the class buttons; **before the class starts**, a group class has a "Ver alumnos" button opening `StudentsDialog.jsx` (per-student accept/reject/cancel + whether they paid) and an individual one just shows the name and payment; once it started that disappears and only "Tomar asistencia" remains (`AttendanceDialog.jsx`: Presente/Ausente per student, "Todos presentes", payment shown); plus the material (`ClassMaterial.jsx`). Payment pill: `utils/bookingStates.js` `paymentStatus`. `Modal` keeps a stack so only the top one handles Escape/Tab.

### The one design decision to understand across front and back: windows → dated availability
A teacher saves windows via `POST/PUT/DELETE /api/teachers/me/availability[/:id]`; `GET /api/teachers/me/availability?from&to` returns the raw windows that fall in the range (the teacher screen places them with `utils/windows.js` `occursOn`). A student books a **date**. **The backend decides what's bookable; the frontend only applies the filters the user picks.** `GET /api/availability?from&to[&excludeBookingId]` returns one row per **(window, date)** that **this** viewer can book, built by one pure function, `bookableRows` in `backend/src/lib/availabilityExpansion.js` (the route only reads from the DB — windows, taken slots, vacations, the viewer's own classes — and calls it). Each row: `{ id, windowId, date, dayKey, teacherId, teacherName, teacherAcceptsRewards, teacherFeatured, start, end, modality, maxStudents, locality, subjects, starts, groups, onVacation }`:
- `subjects: [{ id, name, hourlyRateCents }]` — the teacher's rates in that modality.
- `starts: [{ start, maxMinutes }]` — each `:00`/`:30` start this student can take, with the longest duration that fits (until the window's end, the teacher's next class or **the student's own next class**). Past starts, starts inside a class of the student's and starts without 30 free min are already removed.
- `groups: [{ start, end, subjectId, subjectName, enrolled, maxStudents }]` — only group classes this student can join (seats left measured on the class, same modality, the subject has a rate, not started, not already enrolled, no clash with the student's classes).
- **A row with no `starts` and no `groups` isn't sent** (full, all clashing, already enrolled…): nothing appears greyed out for being full. The exception is vacation: those rows come with `onVacation: true`, empty `starts`/`groups`, and are drawn greyed (a today vacation row whose window already ended is omitted).
- `excludeBookingId` (rescheduling, only if it's the viewer's own `confirmada` booking): the old booking doesn't occupy its slot, and only that teacher and subject are returned.
- Windows whose modality has no rate aren't offered (`db/availability.js` `findPublishedWindows` is the only place of that rule; `db/rates.js` `hasRateInModality`/`ratedSubjectsJson` are the shared SQL).

The frontend doesn't recompute any of this: `utils/booking.js` `filterCards` applies the user's filters (day, subject, modality, individual/group, time, text, favorites), `countBookableByDate` gives the "N para reservar" counts (vacation rows don't count), `filterSubjectsFor` the subject chips. `POST /api/bookings` re-validates everything anyway, because a tab left open keeps showing starts that have since passed.

**Where filters live:** every filter in the code carries a `FILTRO:` comment saying what it hides and who decides (`grep -rn "FILTRO:"`). There are two indexes, which point to each other: the backend one at the top of `backend/src/lib/availabilityExpansion.js`, the frontend one at the top of `frontend/src/utils/booking.js`. Adding, moving or removing a filter means updating its comment and the index.

Everything that isn't `cancelada` occupies the slot, `pendiente` included (`class_bookings_student_no_overlap` is `WHERE status <> 'cancelada'`; `classes_teacher_no_overlap` is `WHERE active`, i.e. some booking isn't cancelled).

Rules the backend must enforce (the UI already does, but the UI can be bypassed): window start/end and class **starts** on `:00`/`:30` (class **ends** land wherever the duration puts them, in steps of 5 min, e.g. 13:45); class duration ≥30 min and within the window; rates in whole cents and only for subjects in the profile (`teacher_rates` FKs `teacher_subjects`, so dropping a subject drops its rates); a teacher's windows can't overlap on any date (weekly vs one-off included — checked in `db/availability.js` under an advisory lock, not a DB constraint); a window's modality must have at least one rate; a teacher never gives two classes at once (`classes_teacher_no_overlap` on active classes; a group class is one row); joining a group requires same subject and duration, plus capacity (checked in `bookClass` under a per-teacher+date lock); a student can't have overlapping classes even by a minute; the booked subject must have a rate in the window's modality.

- Backend: `127.0.0.1:4000`

Use `127.0.0.1`, not `localhost`: on macOS `localhost` resolves to `::1` first, and if any other project's dev server is bound to `[::1]:5173` it silently wins over Docker's wildcard bind. Check with `lsof -nP -iTCP:5173 -sTCP:LISTEN`.

## Commands
Run these from inside the respective subfolder (`frontend/` or `backend/`), not from the repo root — there's no root-level `package.json`.

**Frontend**
- `npm run dev` — Vite dev server (not `npm start`, that's a CRA habit).
- `npm test` — vitest + jsdom + Testing Library. Tests are colocated (`Thing.jsx` → `Thing.test.jsx`).
- `npm run lint` — must pass before pushing, along with `npm test`.
- Test data: build API-shaped objects with `src/testing/fixtures.js` — `apiBooking()` (a booking exactly as `/api/bookings` returns it, with `id` and `classId`), `apiUser()` (as login/`/me`/profile return it) and `updatedUser()` (the `PATCH /api/users/me` response), plus `apiAvailabilityRow()` (a `GET /api/availability` row; `startsBetween(start, end)` builds its `starts`), `apiStudentPack()` (a `GET /api/packs/mine` pack), `apiHomework()`/`apiSubmission()` and `apiNeuronas()`/`apiTeacherNeuronas()` — and override only what the test cares about. Don't hand-write partial classes/users: tests end up passing on a shape the API no longer sends. Mock client functions with the real response shape (unwrapped objects, never `{ user }` / `{ lesson }`).

**Backend**
- Tests: vitest, colocated (`index.js` → `<area>.test.js`), using `buildApp()` + `app.inject()` (no real port). See `src/app.test.js` for the pattern. The `db/*` modules are mocked; mock them with the rows they really return (e.g. `unaReserva()` in `routes/bookings/bookings.test.js` mirrors `BOOKING_COLUMNS`).
- Migrations: plain `.sql` in `migrations/`, no runner. On a **fresh** database volume Postgres applies them all automatically (`docker-compose.dev.yml` mounts the folder into `docker-entrypoint-initdb.d`); on an existing database apply each **new** one by hand, once, in filename order — `psql "$DATABASE_URL" -f migrations/0NN_*.sql` — and tell the team, since everyone has their own local DB. Write new ones idempotently (`IF NOT EXISTS`, guarded `DO` blocks) so an accidental re-run is harmless. **Never re-run 003–006 on an existing database**: they predate later schema changes, fail midway, and since files don't run in a transaction the statements before the failure stick (re-running 006 drops `classes_teacher_no_overlap` before erroring).

**Infra / Docker**
- Dev stack: `docker compose -f docker-compose.dev.yml up --build`.
- After changing dependencies in either app, rebuild with `-V` (not just `--build`): `docker compose -f docker-compose.dev.yml up --build -V`. Both app services mount an anonymous `/app/node_modules` volume that Docker seeds only once and then persists across rebuilds, shadowing a freshly built image's deps — symptom is `Failed to resolve import "<package>"` in the browser/server despite a clean build. **Never use `down -v`** — that also wipes the named `pgdata_dev` volume and deletes the database.

## Cross-cutting conventions
- **Style differs on purpose between the two app repos** — match whichever folder you're editing, don't impose one on the other, and don't run a formatter (neither has a prettier config):
  - `backend/`: semicolons, single quotes, 2-space indent, ~100 cols.
  - `frontend/`: no semicolons, single quotes, 2-space indent, ~100 cols. Class components only — hooks are banned except in the one bridge file `src/routes/withRouter.jsx`, which hands components a single `router` prop (`navigate`, `location`, `params`, `searchParams`, `setSearchParams`).
- **Mobile UI (≤700px, `MOBILE_QUERY` in `utils/media.js`; keep it in sync with the `@media (max-width: 700px)` blocks)** is a separate iOS-inspired layout, not just restyled desktop: floating 5-tab bar (Favoritos and the theme toggle live in Perfil), `components/WeekStrip.jsx` instead of the month grid (`MonthPane`/`WeekCalendar` with a "Mes" toggle), modals become bottom sheets (CSS + drag-to-close in `Modal.jsx`), Reservar has its own search + quick chips + a filters sheet. Components that render differently get a `mobile` prop from `routes/withViewport.jsx` (a class HOC, not a hook); jsdom has no `matchMedia`, so tests are desktop unless they pass `mobile` explicitly. 700–900px (tablets) keeps the older narrow-desktop layout. The Calendar's side panel (`DayAgenda`) lists **all** classes of the loaded range grouped by day; picking a day scrolls to it, it doesn't filter.
- **IDs are opaque UUID strings** (`gen_random_uuid()`), never numbers — don't coerce with `Number()`, compare with `String(a) === String(b)`. On the backend, validate ids and dates with `backend/src/lib/validators.js` (`isUuid`, `isRealDate`, `ISO_DATE_RE`, `UUID_RE`) instead of a local regex: a malformed id or an impossible date like `2026-02-30` would otherwise reach Postgres as a 500.
- **Dates** are `"YYYY-MM-DD"` local time, no timezone/`Z`. "Now" on the backend is Argentina time via `backend/src/lib/clock.js` — the container runs in UTC, so never use `new Date()` getters or `toISOString()` for today. **Times** are `"HH:MM"` 24h; starts are always `:00`/`:30`, a class end can be any minute. A range's `end` is exclusive; midnight is written `"24:00"`, never `"00:00"`. Weekday keys are ASCII lowercase without accents (`lunes` … `domingo`), week starts Monday — these are JSON/DB values, not display text.
- Check `pwd` before `npm install` — `package-lock.json` has repeatedly ended up committed to the wrong subfolder.
- No backwards-compatibility code for old data shapes: every migration is applied to every DB, so the frontend can rely on the schema as it is now (e.g. a class always has `modality`, `maxStudents` and `priceCents` — `NOT NULL` since 009). Don't add "legacy row" branches; if old data needs handling, fix it in a migration.
